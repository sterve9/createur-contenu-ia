## 1. Objectif du document

Ce document formalise la stratégie de tests, les scénarios et les
jeux de données nécessaires pour valider l'ensemble de la V2.

Il permet à toute personne — développeur, testeur, auditeur — de :
- comprendre ce qui est testé et pourquoi ;
- reproduire les tests dans un environnement propre ;
- vérifier que les garanties structurantes V2 sont respectées ;
- confirmer que la V1 n'est en aucun cas altérée par la V2.

Il ne décrit pas les résultats d'exécution des tests. Ceux-ci sont
consignés séparément dans un rapport d'exécution.

---

## 2. Stratégie de tests

### 2.1 Pyramide de tests V2

La stratégie de tests V2 suit la pyramide classique :

```
                     ▲
                    /E2E\               3 scénarios bout-en-bout
                   /─────\
                  / Intég \              7 tests d'intégration
                 /─────────\
                /  Unitaires \           6 tests unitaires ciblés
               /─────────────\
              / Non-régression\          4 tests de non-régression V1
             /─────────────────\
            /   Idempotence     \        5 tests d'idempotence
           /─────────────────────\
          /      Résilience       \      6 tests de résilience isolée
         /─────────────────────────\
```

### 2.2 Niveaux de tests

| Niveau | Objet | Nombre approximatif |
|---|---|---|
| **Unitaire** | Nœuds à logique complexe (normalisations JS, validations) | 6 |
| **Intégration** | Comportement complet d'un workflow | 7 |
| **Bout-en-bout (E2E)** | Cycle complet d'une campagne V2 | 3 |
| **Non-régression V1** | Preuve que V2 ne modifie pas V1 | 4 |
| **Idempotence** | Preuve qu'une relance ne crée pas de doublons | 5 |
| **Résilience** | Preuve que l'isolation par plan fonctionne | 6 |

### 2.3 Environnement de tests

Les tests sont exécutés dans un environnement dédié aux tests :

- Base PostgreSQL / Supabase de test (séparée de la production)
- Instance n8n de test avec les workflows V2 déployés
- Credentials API isolés (Anthropic, YouTube)
- Fixtures V1 chargées avant chaque campagne de tests

## 4. Tests unitaires

### TU-01 · Normalisation des scènes — cas nominal

**Nœud testé** : C-V2-07 · Normaliser Scènes

**Objectif** : Vérifier que le nœud parse correctement un JSON
valide et retourne un tableau d'items formatés.

**Prérequis** : Aucun.

**Données d'entrée** :
```json
{
  "content": [
    {
      "type": "text",
      "text": "{\"scenes\":[{\"numero_scene\":1,\"texte_narratif\":\"Test\",\"ambiance_visuelle\":\"Dynamique\",\"duree_estimee\":10}]}"
    }
  ]
}
```

**Résultat attendu** :
- 1 item retourné
- L'item contient `dossier_id`, `numero_scene=1`, `texte_narratif="Test"`, `ambiance_visuelle="Dynamique"`, `duree_estimee=10`
- Aucune exception levée

**Critère de validation** : Sortie strictement conforme au format attendu.

## 7. Tests de non-régression V1

### TNR-01 · Aucune modification des tables V1 après une campagne V2

**Objectif** : Prouver que V2 ne modifie jamais V1.

**Étape 1 — Baseline** : Capturer un hash de chaque table V1 avant
toute campagne V2 :
```sql
SELECT
  (SELECT MD5(CAST((array_agg(campagnes.*)) AS TEXT)) FROM campagnes) AS h_camp,
  (SELECT MD5(CAST((array_agg(contenus.*)) AS TEXT)) FROM contenus) AS h_cont,
  (SELECT MD5(CAST((array_agg(analyses.*)) AS TEXT)) FROM analyses) AS h_anal,
  (SELECT MD5(CAST((array_agg(scripts.*)) AS TEXT)) FROM scripts) AS h_scri,
  (SELECT MD5(CAST((array_agg(journal_execution.*)) AS TEXT)) FROM journal_execution) AS h_jour;
```

**Étape 2** : Exécuter TE2E-01 complète.

**Étape 3 — Vérification** : Recalculer les hashes.

**Résultat attendu** : Les 5 hashes sont strictement identiques
avant et après la campagne V2.

**Critère de validation** : Aucun octet des tables V1 n'a bougé.

### TNR-04 · Suppression d'un dossier V2 ne casse pas la campagne V1

## 9. Tests de résilience isolée

**Objectif** : Vérifier que si le plan 2 échoue à la génération

**Procédure** : Simuler une réponse IA invalide uniquement pour

**Résultat attendu** :
- `v2_plans` : plan 2 a `statut = 'ERREUR'`, les autres plans
  ont `statut = 'COMPLET'`
- `v2_prompts_images` : lignes présentes pour tous les plans
  SAUF le plan 2
- `v2_prompts_animations` : lignes présentes pour tous les plans

- `v2_dossiers_production.statut = 'TERMINE'`
- `v2_dossiers_production.nb_plans_traites = nb_plans_total`

**Critère de validation** : L'isolation fonctionne, la campagne
se clôture malgré l'erreur.

### TR-02 · Erreur sur le prompt animation du plan 3

**Objectif** : Vérifier que si le plan 3 échoue à la génération
de son prompt animation, les autres plans ne sont pas impactés.

**Procédure** : Simuler une erreur uniquement sur le workflow
V2-ANIM pour le plan 3.

**Résultat attendu** :

- 1 ligne dans `v2_journal_execution`
- Dossier clôturé en `TERMINE`

**Critère de validation** : L'isolation fonctionne, l'erreur est
localisée à un seul plan.

### TR-03 · Erreur totale sur la génération des scènes

**Objectif** : Vérifier le comportement si l'IA échoue avant même
la création de scènes.

**Note** : ce cas relève d'une reprise manuelle via le Dashboard.

---

### TR-04 · Erreur sur la persistance d'une scène

**Objectif** : Vérifier le comportement si l'INSERT en base échoue
pour une scène spécifique.

**Procédure** : Provoquer une violation de contrainte (par exemple
en insérant deux scènes avec le même `numero_scene` sans utiliser
le `ON CONFLICT`).

**Résultat attendu** :
- L'erreur est capturée par V2-ERR
- La scène en conflit est rejetée
- Les autres scènes déjà insérées restent en base

**Critère de validation** : Une erreur d'insertion n'annule pas
les insertions précédentes.

---

### TR-05 · Erreur sur le générateur de descriptions

**Objectif** : Vérifier que si le workflow V2-PUB échoue, le

- Toutes les autres tables sont correctement peuplées
- 1 ligne dans `v2_journal_execution` mentionnant C-V2-20
- Le dossier est en `TERMINE` (les prompts sont utilisables)

**Critère de validation** : L'échec de V2-PUB ne bloque pas la
promesse principale du Kit Créateur (les prompts).

---

### TR-06 · Erreurs multiples sur plusieurs plans

**Objectif** : Vérifier que plusieurs erreurs simultanées sur
différents plans sont toutes gérées de façon isolée.

**Procédure** : Simuler une erreur sur les plans 2 et 4
(prompt image pour l'un, prompt animation pour l'autre).

**Résultat attendu** :
- Plan 2 : `statut = 'ERREUR'`, pas de prompt image ni animation
- Plan 4 : `statut = 'ERREUR'`, prompt image présent mais pas d'animation
- Plans 1, 3, 5... : `statut = 'COMPLET'`
- 2 lignes distinctes dans `v2_journal_execution`
- Dossier clôturé en `TERMINE`
- `nb_plans_traites = nb_plans_total` (les échecs comptent comme
  traités)

**Critère de validation** : Chaque erreur est isolée et traçable
individuellement.

## 11. Critères d'acceptation V2

La V2 est considérée comme validée si :

- **100 % des tests P0 passent** (25 tests)
- **80 % au minimum des tests P1 passent** (6 tests)
- **Aucun test de non-régression V1 n'échoue**
- **Aucun test d'idempotence n'échoue**
- **Aucun test de résilience isolée n'échoue**

En cas d'échec d'un test P0, la V2 est bloquée en déploiement
jusqu'à correction.

---

## 12. Règles de gouvernance du plan de tests

| Règle | Description |
|---|---|
| R-TEST-01 | Chaque test est exécutable à partir des fixtures documentées, sans dépendance externe. |
| R-TEST-02 | Les résultats attendus sont vérifiables par requête SQL ou inspection directe de la base. |
| R-TEST-03 | Un test P0 en échec bloque le déploiement V2. |
| R-TEST-04 | Les tests de non-régression V1 doivent être rejoués à chaque évolution V2. |
| R-TEST-05 | Les tests d'idempotence doivent être rejoués à chaque modification d'un `ON CONFLICT`. |
| R-TEST-06 | Ajouter un nouveau composant V2 impose d'ajouter au minimum : 1 test unitaire ciblé, 1 test d'intégration, 1 mise à jour du scénario E2E. |
