# 02.4.V2 — Mapping des Données (V2)

## Rôle du document

Ce document établit la correspondance précise entre :
- les **objets métier V2** (définis dans `02.1.V2`) ;
- les **attributs métier V2** (définis dans `02.2.V2`) ;
- les **tables et colonnes physiques V2** (définies dans `02.3.V2`).

Il répond aux questions suivantes :

- À quelle table physique correspond chaque objet métier V2 ?
- À quelle colonne physique correspond chaque attribut métier V2 ?
- Quels sont les écarts de nommage entre couche métier et couche physique ?
- Pour chaque colonne V2, quel composant l'écrit et quels composants la lisent ?
- Comment les références vers les objets V1 sont-elles matérialisées ?

Ce document ne décrit jamais :
- les types de données SQL (relèvent du schéma physique) ;
- les contraintes techniques (relèvent du schéma physique) ;
- les workflows n8n (relèvent de l'architecture des workflows) ;
- les implémentations techniques.

---

## 1. Positionnement par rapport à la V1

Ce mapping complète celui de la V1 (`02.4_Mapping_des_Donnees.md`) sans le modifier.
Les mappings V1 (Campagne ↔ `campagnes`, Script ↔ `scripts`, etc.) restent valides et sont réutilisés tels quels.

Seuls les mappings des **nouveaux objets V2** sont documentés ici.

## 12. Mapping des références vers les objets V1

La V2 référence deux objets V1 principaux. Le mapping des références est le suivant :

| Référence métier V2 | Colonne V2 | Table V1 cible | Colonne V1 cible | Cardinalité |
|--------------------|------------|----------------|------------------|-------------|
| Dossier → Campagne | `v2_dossiers_production.campagne_id` | `campagnes` | `campagnes.id` (BIGINT) | Un dossier → une campagne ; une campagne → 0 à N dossiers |
| Dossier → Script | `v2_dossiers_production.script_id` | `scripts` | `scripts.id` (INTEGER) | Un dossier → un script ; un script → 0 à N dossiers |

**Note technique** : la colonne `v2_dossiers_production.script_id` est en `INTEGER` pour respecter le typage réel de `scripts.id` (héritage V1). Ce choix est documenté dans `02.3.V2` (section "Anomalies V1 non répliquées en V2").

## 13. Récapitulatif des écarts de nommage systématiques

Les correspondances suivantes sont **systématiques** dans tout le mapping V2 :

| Attribut métier V2 | Colonne physique V2 | Raison |
|-------------------|--------------------|---------|
| `xxx_id` (identifiant principal d'un objet) | `id` | Convention SQL standard |
| `date_creation` | `created_at` | Convention Supabase / PostgreSQL |
| `date_derniere_modification` | `updated_at` | Convention Supabase / PostgreSQL |
| `date_generation` | `created_at` | Convention Supabase (une seule colonne technique pour toutes les dates de création) |
| `date_ajout_catalogue` | `created_at` | Même logique |

Ces écarts ne posent aucun problème métier : le vocabulaire métier reste expressif, et le vocabulaire physique reste normalisé.

## 14. Récapitulatif des composants écrivains

Pour chaque colonne, un et un seul composant a la responsabilité d'écrire la donnée initiale :

| Composant | Écrit dans |
|-----------|------------|
| **Création de Campagne** | `v2_dossiers_production` (colonnes de création : `campagne_id`, `script_id`, `outil_image_id`, `outil_animation_id`, `statut`) |
| **Sélection de Script** | `v2_dossiers_production.script_id` (déclenche la création du dossier) |
| **Découpage en Scènes** | `v2_scenes` (toutes colonnes) |
| **Composant Plans** | `v2_plans` (toutes colonnes) |
| **Générateur Prompts Images** | `v2_prompts_images` (toutes colonnes) |
| **Générateur Prompts Animations** | `v2_prompts_animations` (toutes colonnes) |
| **Générateur Descriptions** | `v2_descriptions_publication` (toutes colonnes) |
| **Gestion du Catalogue** | `v2_outils` (toutes colonnes) |
| **Création automatique de la Checklist** | `v2_checklists` + `v2_etapes_checklist` (initialisation) |
| **Dashboard** | `v2_dossiers_production.statut`, `v2_dossiers_production.updated_at`, `v2_etapes_checklist.est_realisee`, `v2_etapes_checklist.date_realisation`, `v2_checklists.updated_at` |
| **Base (DEFAULT)** | Tous les `created_at` et valeurs par défaut définies au niveau du schéma |

Aucune colonne V2 n'est écrite par deux composants différents (règle d'unicité d'écriture).

## 15. Récapitulatif des composants lecteurs principaux

| Composant | Lit principalement |
|-----------|-------------------|
| **Création de Campagne** | `v2_outils` (pour proposer les choix) |
| **Générateurs Prompts** | `v2_scenes`, `v2_plans`, `v2_outils`, `v2_dossiers_production` |
| **Générateur Descriptions** | `v2_dossiers_production`, `scripts` (V1) |
| **Dashboard** | Toutes les tables V2, plus les tables V1 (`campagnes`, `scripts`) |

Le Dashboard est le composant **lecteur universel** : il agrège l'ensemble des données V1 et V2 pour offrir une vue unifiée au créateur.

---

## 16. Validation

Le mapping V2 est considéré comme valide lorsque :

- chaque objet métier V2 est mis en correspondance avec exactement une table physique V2 ;
- chaque attribut métier V2 est mis en correspondance avec exactement une colonne physique V2 ;
- tous les écarts de nommage sont identifiés et documentés ;
- pour chaque colonne V2, un composant écrivain unique est identifié ;
- pour chaque colonne V2, les composants lecteurs sont explicités ;
- les références aux objets V1 (`campagnes`, `scripts`) sont correctement mappées ;
- aucun objet ou attribut V2 n'est absent du mapping ;
- aucune technologie d'implémentation n'apparaît dans ce document.
