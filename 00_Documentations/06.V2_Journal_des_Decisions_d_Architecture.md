### ADR-V2-01 — Hiérarchie de vérité documentaire

#### Contexte
Lors de la conception V2, des divergences ont été identifiées entre :
- Le document `V2-008` (architecture métier — vocabulaire logique)
- Le document `V2-010` (implémentation technique — vocabulaire opérationnel)
- La réalité du schéma Supabase en production

#### Décision
La hiérarchie de vérité est établie de manière stricte, **de la plus forte à la plus faible** :
$$\text{Supabase (Réel)} > \text{V2-010 (Implémentation)} > \text{V2-008 (Architecture métier)}$$

**Règles dérivées :**
- Le terme `v2_campagnes` est **BANNI** (il n'existe pas en base).
- Le terme officiel retenu est `v2_dossiers_production`.
- L'architecture V2 comporte officiellement **7 workflows logiques** :  
  `V2-ORCH`, `V2-SCENE`, `V2-PLAN`, `V2-IMG`, `V2-ANIM`, `V2-PUB`, `V2-ERR`.
- `V2-ORCH` comporte 7 nœuds logiques (C-V2-01 à C-V2-05b).

#### Conséquences
- Toute contradiction entre documents se résout **en faveur du schéma Supabase**.
- Les documents V2-008 et V2-010 doivent être mis à jour dès qu'un écart est détecté.

#### Alternatives rejetées
- *Rendre V2-008 prioritaire* → Rejeté : trop conceptuel, risque de créer une dette technique face à la base réelle.

### ADR-V2-02 — Pattern d'orchestration n8n

#### Contexte
V2-008 décrit 6 workflows métier distincts (ORCH, SCENE, PLAN, IMG, ANIM, PUB).  
*Problématique* : Faut-il implémenter 6 workflows n8n séparés ou 1 seul workflow monolithique ?

#### Décision
**1 seul workflow n8n monolithique**, nommé :  
`V2 — Créateur de Dossier de Production`

Il contient tous les nœuds C-V2-01 à C-V2-22, regroupés visuellement par **Sticky Notes colorées** (une par bloc fonctionnel ORCH/SCENE/PLAN/IMG/ANIM/PUB).

> **Exception** : `V2-ERR` reste un workflow séparé, rattaché globalement comme `errorWorkflow`.

#### Conséquences
- Debug centralisé (1 seule exécution à suivre sur n8n).
- Aucune latence inter-workflow (appels HTTP internes évités).
- Structure visuelle très lisible grâce à l'organisation par zones.

#### Alternatives rejetées
- *6 workflows séparés reliés par HTTP* → Rejeté : trop complexe, latence inutile, debug fragmenté.
- *6 sous-workflows (`Execute Workflow` node)* → Rejeté : perte de visibilité lors des sessions de debug.

### ADR-V2-03 — Correction C-V2-03 : alignement sur les FK réelles de la V1

#### Contexte
Le document V2-010 (version initiale) proposait pour C-V2-03 la requête :
```sql
SELECT ... FROM scripts s
JOIN campagnes c ON c.id = s.campagne_id;
Problème détecté lors de l'audit du 06/08/2026 : La table scripts n'a pas de FK directe vers campagnes.

Décision (Initiale — 06/08/2026)
La requête C-V2-03 utilise le chemin FK réel :

SQL
SELECT ... FROM scripts s
JOIN analyses a ON a.id = s.analyse_id
JOIN contenus co ON co.id = a.contenu_id
JOIN campagnes c ON c.id = co.campagne_id;
Chemin FK : scripts.analyse_id → analyses.id → analyses.contenu_id → contenus.id → contenus.campagne_id → campagnes.id.

🔄 Révision ADR-V2-03 (07/08/2026)

Après vérification empirique des données réelles dans Supabase (19/19 lignes testées) :

SQL
SELECT COUNT(*) FROM scripts s
JOIN analyses a ON a.id = s.analyse_id
WHERE s.contenu_id = a.contenu_id;
-- Résultat : 19/19 (100% identiques)
Constat : scripts.contenu_id est peuplé à 100% et strictement identique à analyses.contenu_id pour toutes les lignes existantes.

Décision de révision : Le chemin FK est simplifié à :

SQL
SELECT ... FROM scripts s
JOIN contenus co ON co.id = s.contenu_id
JOIN campagnes ca ON ca.id = co.campagne_id;
Chemin FK simplifié : scripts.contenu_id → contenus.id → contenus.campagne_id → campagnes.id (2 JOINs au lieu de 3).

Justification & Impact
Conformité ADR-V2-01 : Supabase réel > V2-010. La simplification est valide.

Performance & Robustesse : Moins de JOINs = exécution plus rapide et moins de points de défaillance.

Impact : 05.V2_Implementation_Technique.md mis à jour et validé en test dans V2-ORCH le 07/08/2026.

ADR-V2-04 — Vérification stricte ID ↔ catégorie pour les outils
Contexte
Lors de la validation fonctionnelle de V2-ORCH (07/08/2026), un bug métier a été identifié dans C-V2-04.

Bug initial : La requête vérifiait l'existence de 2 outils dans le lot sans contrôler que outil_image_id appartienne bien à la catégorie image (et vice-versa pour l'animation).

Cas de bug reproductible :

L'utilisateur envoie outil_image_id = 5 (Kling AI = outil animation en réalité).

L'utilisateur envoie outil_animation_id = 1 (Playground AI = outil image en réalité).

Le total retournait 2 outils valides (1 image + 1 animation), passant le filtre IF alors que les IDs étaient inversés.

Décision
La requête C-V2-04 utilise des COUNT FILTER explicites vérifiant le couple (ID, catégorie) :

SQL
SELECT
  COUNT(*) FILTER (
    WHERE id = <outil_image_id>
      AND categorie = 'image'
  ) AS nb_image_valide,
  COUNT(*) FILTER (
    WHERE id = <outil_animation_id>
      AND categorie = 'animation'
  ) AS nb_animation_valide,
  STRING_AGG(nom || ' (' || categorie || ')', ', ') AS outils_trouves
FROM v2_outils
WHERE id IN (<outil_image_id>, <outil_animation_id>)
  AND actif = true;
Un nœud IF · Outils Valides ? est placé en aval avec 2 conditions strictes :

nb_image_valide == 1

nb_animation_valide == 1 (avec combinateur AND).

Conséquences
Rejet immédiat en amont si les IDs d'outils sont inversés ou mal typés.

Test négatif validé le 07/08/2026 : IDs inversés → False Branch → 0 dossier créé en base.

Alternatives rejetées
Vérification simple COUNT(*) = 2 → Rejeté : n'intercepte pas les inversions d'IDs.

Contrainte CHECK en base de données → Rejeté : nécessiterait une jointure runtime coûteuse.

ADR-V2-05 — Cardinalité 1-item obligatoire à la sortie de chaque bloc
Contexte
n8n applique par défaut la règle "1 item entrant = 1 exécution du nœud suivant". Lorsqu'un nœud Postgres retourne N lignes, les nœuds en aval s'exécutent N fois en parallèle.

Bug identifié le 07/08/2026 : C-V2-04 initial retournait 2 lignes. Résultat : C-V2-05 et C-V2-05b se sont exécutés 2 fois chacun, créant 2 dossiers au lieu d'1 et 18 étapes de checklist au lieu de 9.

Décision
Règle architecturale : Chaque bloc fonctionnel (ORCH, SCENE, PLAN, IMG, ANIM, PUB) doit garantir en sortie 1 seul item n8n, prêt à être consommé par le bloc suivant.

Méthode privilégiée : Agrégation SQL via CTE + SELECT récapitulatif.

SQL
WITH insertions AS (
  INSERT INTO v2_etapes_checklist (checklist_id, libelle, ordre_affichage, est_realisee)
  VALUES
    (<checklist_id>, 'Scènes générées', 1, false),
    -- ...
    (<checklist_id>, 'Publication préparée', 9, false)
  RETURNING id, checklist_id
)
SELECT
  <checklist_id> AS checklist_id,
  COUNT(*)::integer AS nb_etapes_creees,
  <dossier_id> AS dossier_id
FROM insertions;
Conséquences
Zéro fan-out involontaire entre les blocs.

Les blocs deviennent parfaitement isolables et déterministes.

Alternatives rejetées
Nœud Aggregate n8n systématique → Rejeté : ajoute un nœud parasite dans la vue.

LIMIT 1 sur les requêtes → Rejeté : masquage de symptômes, perte de données.

ADR-V2-06 — Pattern Aggregate + .first() pour les barrières de phase
Contexte
Problèmes rencontrés lors de l'implémentation de C-V2-11b (08/08/2026) :

Fan-out post-LLM : C-V2-11 émet N items (18 plans pour le test). Sans agrégation, le nœud d'update C-V2-11b s'exécuterait 18 fois inutilement.

Rupture des Paired Items : Après un nœud Aggregate n8n, la référence $('Nœud').item.json.champ échoue avec l'erreur "Paired item data unavailable".

Décision
Adoptée pour toutes les barrières de phase et nœuds post-agrégation :

Nœud Aggregate obligatoire avant chaque barrière de phase :

Mode : All Item Data (Into a Single List)

Output Field : <nom_metier>_persistes

Syntaxe .first() obligatoire post-Aggregate :

Remplacer systématiquement $('Nœud').item.json.champ par $('Nœud').first().json.champ.

Conséquences
Conforme à ADR-V2-05 (garantit 1 item en sortie de bloc).

Suppression définitive des erreurs de traçabilité n8n (Paired item data).

ADR-V2-07 — Fusion outil ↔ plans dans un SELECT unique (V2-IMG)
Contexte
Implémentation du bloc V2-IMG (09/08/2026). Initialement, C-V2-14 devait lire v2_outils séparément après C-V2-13 (SELECT des plans).

Problème : Exécuter un nœud SQL secondaire après un fan-out (18 plans) déclenchait 18 requêtes identiques sur v2_outils.

Décision
Suppression du nœud séparé C-V2-14 et fusion directe de la lecture outil dans la requête amont C-V2-13 via un JOIN :

SQL
SELECT 
  p.*,
  o.conventions_prompt,
  o.nom AS nom_outil
FROM v2_plans p
JOIN v2_dossiers_production d ON d.id = p.dossier_id
JOIN v2_outils o ON o.id = d.outil_image_id 
  AND o.categorie = 'image' 
  AND o.actif = true
WHERE p.dossier_id = <dossier_id>;
Règle générale émergente
Toute donnée de contexte partagée (outil, configuration, référentiel) doit être fusionnée dans le SELECT amont du bloc plutôt que d'être lue dans un nœud séparé placé après un fan-out.

Conséquences
1 seule lecture DB, 0 duplication de requêtes, performance optimale.

Le JOIN inclut la vérification categorie = 'image', renforçant ADR-V2-04.

Le code de nœud C-V2-14 reste vacant dans la documentation par souci de traçabilité.

Pattern à répliquer sur V2-ANIM (C-V2-16 / outil_animation_id).
