## Rôle du document

Ce journal historise **les décisions d'architecture significatives**
prises pendant la conception et le développement de la V2.

Chaque ADR (Architecture Decision Record) répond à trois questions :
- **Quel problème** ou quelle ambiguïté a déclenché la décision ?
- **Quelle décision** a été prise, et pourquoi ?
- **Quelles conséquences** cette décision entraîne pour l'implémentation ?

Les ADR sont **immuables** une fois validés. Une évolution ultérieure
se fait par un nouvel ADR qui référence et annule le précédent.

## ADR-V2-01 — Hiérarchie de vérité documentaire V2

**Statut** : ✅ Acté
**Date** : 2026-08-06
**Décideur** : Sterve
**Contexte de la décision** : Reprise de la phase V2-DEV

### Problème

Au démarrage de l'implémentation des workflows V2 dans n8n, une lecture
croisée des documents de conception a révélé plusieurs divergences
entre `03.V2_Architecture_des_Workflows.md` (V2-008) et
`05.V2_Implementation_Technique.md` (V2-010) :

- V2-008 nomme la table centrale `v2_campagnes` ; V2-010 utilise
  `v2_dossiers_production`.
- V2-010 ajoute un nœud C-V2-04 (Vérifier Outils V2) absent de V2-008,
  ce qui décale la numérotation des nœuds suivants (Créer Dossier V2
  passe de C-V2-04 à C-V2-05).
- V2-010 introduit le nœud C-V2-05b (Créer Checklist) et le workflow
  V2-PUB (C-V2-20 à C-V2-22), tous deux absents de V2-008.
- Le schéma physique réel dans Supabase correspond à V2-010, pas à
  V2-008.

Sans règle claire, tout nœud implémenté risque de se référer à un
nom de table ou de colonne inexistant, ce qui provoquerait des erreurs
d'exécution silencieuses en base.

### Décision

La hiérarchie de vérité suivante s'applique de manière **absolue** à
partir de ce jour, sur tous les documents et toutes les phases V2 :

1. 🥇 **Schéma Supabase réel** — la vérité opérationnelle.
2. 🥈 **`05.V2_Implementation_Technique.md` (V2-010)** — le document
    d'implémentation, aligné sur Supabase.
3. 🥉 **`03.V2_Architecture_des_Workflows.md` (V2-008)** — le document
    d'architecture métier, utile pour comprendre l'intention mais
    obsolète sur les noms techniques.

**Corollaires directs** :
- Le terme `v2_campagnes` est **définitivement banni** de tout code,
  requête SQL, prompt IA ou nom de nœud.
- Le terme officiel est `v2_dossiers_production`, aligné avec le
  vocabulaire métier "dossier de production" acté en V2-002.
- Le workflow V2-ORCH comporte officiellement **7 nœuds** :
  C-V2-01, C-V2-02, C-V2-03, C-V2-04, C-V2-05, C-V2-05b (+ un IF
  implicite après C-V2-03).
- L'architecture V2 comporte officiellement **7 workflows** :
  V2-ORCH, V2-SCENE, V2-PLAN, V2-IMG, V2-ANIM, V2-PUB, V2-ERR.

### Conséquences

- **Positive** : Toute ambiguïté nom-de-table / nom-de-colonne est
  levée. Un seul document (V2-010) sert de référence unique pour
  l'implémentation.
- **Positive** : Toute évolution future du schéma se fait par
  modification de V2-010 (et de Supabase), sans avoir à toucher V2-008.
- **Négative** : V2-008 devient partiellement obsolète. À traiter
  lors d'une future séance de nettoyage documentaire (non prioritaire :
  ce document reste précieux pour la compréhension métier).
- **Action requise** : Marquer explicitement V2-008 comme "document
  d'architecture métier — pour référence conceptuelle uniquement,
  voir V2-010 pour l'implémentation".

## ADR-V2-02 — Pattern d'orchestration n8n : workflow monolithique

**Statut** : ✅ Acté
**Date** : 2026-08-06
**Décideur** : Sterve
**Contexte de la décision** : Reprise de la phase V2-DEV

### Problème

V2-008 décrit **7 workflows fonctionnels** (V2-ORCH, V2-SCENE,
V2-PLAN, V2-IMG, V2-ANIM, V2-PUB, V2-ERR), organisés par
responsabilité métier.

Cette description peut se traduire techniquement dans n8n de deux
façons radicalement différentes :

- **Option A — 7 workflows n8n physiques distincts**, appelés en
  cascade via des nœuds "Execute Workflow" ou des webhooks internes.
- **Option B — 1 seul workflow n8n monolithique**, regroupant tous
  les nœuds C-V2-01 à C-V2-22, avec des Sticky Notes pour matérialiser
  visuellement les blocs fonctionnels.

Le choix conditionne toute l'implémentation à venir, notamment la
gestion du contexte entre nœuds et la stratégie de gestion d'erreur.
