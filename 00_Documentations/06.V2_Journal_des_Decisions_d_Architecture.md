## Rôle du document

Ce journal historise **les décisions d'architecture significatives**
prises pendant la conception et le développement de la V2.

Chaque ADR (Architecture Decision Record) répond à trois questions :
- **Quel problème** ou quelle ambiguïté a déclenché la décision ?
- **Quelle décision** a été prise, et pourquoi ?
- **Quelles conséquences** cette décision entraîne pour l'implémentation ?

Les ADR sont **immuables** une fois validés. Une évolution ultérieure
se fait par un nouvel ADR qui référence et annule le précédent.

## ADR-V2-01 — Hiérarchie de vérité documentaire V2

**Statut** : ✅ Acté
**Date** : 2026-08-06
**Décideur** : Sterve
**Contexte de la décision** : Reprise de la phase V2-DEV

### Problème

Au démarrage de l'implémentation des workflows V2 dans n8n, une lecture
croisée des documents de conception a révélé plusieurs divergences
entre `03.V2_Architecture_des_Workflows.md` (V2-008) et
`05.V2_Implementation_Technique.md` (V2-010) :

- V2-008 nomme la table centrale `v2_campagnes` ; V2-010 utilise
  `v2_dossiers_production`.
- V2-010 ajoute un nœud C-V2-04 (Vérifier Outils V2) absent de V2-008,
  ce qui décale la numérotation des nœuds suivants (Créer Dossier V2
  passe de C-V2-04 à C-V2-05).
- V2-010 introduit le nœud C-V2-05b (Créer Checklist) et le workflow
  V2-PUB (C-V2-20 à C-V2-22), tous deux absents de V2-008.
- Le schéma physique réel dans Supabase correspond à V2-010, pas à
  V2-008.

Sans règle claire, tout nœud implémenté risque de se référer à un
nom de table ou de colonne inexistant, ce qui provoquerait des erreurs
d'exécution silencieuses en base.

### Décision

La hiérarchie de vérité suivante s'applique de manière **absolue** à
partir de ce jour, sur tous les documents et toutes les phases V2 :

1. 🥇 **Schéma Supabase réel** — la vérité opérationnelle.
2. 🥈 **`05.V2_Implementation_Technique.md` (V2-010)** — le document
    d'implémentation, aligné sur Supabase.
3. 🥉 **`03.V2_Architecture_des_Workflows.md` (V2-008)** — le document
    d'architecture métier, utile pour comprendre l'intention mais
    obsolète sur les noms techniques.

**Corollaires directs** :
- Le terme `v2_campagnes` est **définitivement banni** de tout code,
  requête SQL, prompt IA ou nom de nœud.
- Le terme officiel est `v2_dossiers_production`, aligné avec le
  vocabulaire métier "dossier de production" acté en V2-002.
- Le workflow V2-ORCH comporte officiellement **7 nœuds** :
  C-V2-01, C-V2-02, C-V2-03, C-V2-04, C-V2-05, C-V2-05b (+ un IF
  implicite après C-V2-03).
- L'architecture V2 comporte officiellement **7 workflows** :
  V2-ORCH, V2-SCENE, V2-PLAN, V2-IMG, V2-ANIM, V2-PUB, V2-ERR.

### Conséquences

- **Positive** : Toute ambiguïté nom-de-table / nom-de-colonne est
  levée. Un seul document (V2-010) sert de référence unique pour
  l'implémentation.
- **Positive** : Toute évolution future du schéma se fait par
  modification de V2-010 (et de Supabase), sans avoir à toucher V2-008.
- **Négative** : V2-008 devient partiellement obsolète. À traiter
  lors d'une future séance de nettoyage documentaire (non prioritaire :
  ce document reste précieux pour la compréhension métier).
- **Action requise** : Marquer explicitement V2-008 comme "document
  d'architecture métier — pour référence conceptuelle uniquement,
  voir V2-010 pour l'implémentation".

## ADR-V2-02 — Pattern d'orchestration n8n : workflow monolithique

**Statut** : ✅ Acté
**Date** : 2026-08-06
**Décideur** : Sterve
**Contexte de la décision** : Reprise de la phase V2-DEV

### Problème

V2-008 décrit **7 workflows fonctionnels** (V2-ORCH, V2-SCENE,
V2-PLAN, V2-IMG, V2-ANIM, V2-PUB, V2-ERR), organisés par
responsabilité métier.

Cette description peut se traduire techniquement dans n8n de deux
façons radicalement différentes :

- **Option A — 7 workflows n8n physiques distincts**, appelés en
  cascade via des nœuds "Execute Workflow" ou des webhooks internes.
- **Option B — 1 seul workflow n8n monolithique**, regroupant tous
  les nœuds C-V2-01 à C-V2-22, avec des Sticky Notes pour matérialiser
  visuellement les blocs fonctionnels.

Le choix conditionne toute l'implémentation à venir, notamment la
gestion du contexte entre nœuds et la stratégie de gestion d'erreur.

### Facteur déterminant

V2-010 utilise systématiquement la syntaxe n8n :
{{ $('Créer Dossier V2').item.json.dossier_id }}
{{ $('Lire Contexte V1').item.json.theme }}
{{ $('Persister Prompt Image').item.json.texte_prompt }}

text


Cette syntaxe **ne fonctionne QUE si les nœuds référencés
appartiennent au même workflow n8n**. Toute autre architecture
imposerait une réécriture complète de V2-010.

### Décision

L'architecture V2 est implémentée sous la forme d'**un unique workflow
n8n monolithique**, contenant l'intégralité des nœuds C-V2-01 à
C-V2-22.

Les **6 blocs fonctionnels** décrits par V2-008 (ORCH, SCENE, PLAN,
IMG, ANIM, PUB) sont matérialisés visuellement dans le workflow n8n
par des **Sticky Notes** colorées, comme cela a été fait pour V2-ERR.

Le **7e workflow (V2-ERR)** reste un workflow n8n séparé, car il
utilise le nœud spécifique `Error Trigger`, qui doit être isolé et
attaché comme `errorWorkflow` au workflow monolithique principal.

### Nom officiel du workflow monolithique

**`V2 — Créateur de Dossier de Production`**

### Conséquences

- **Positive** : Aucune modification de V2-010 nécessaire. Toutes les
  expressions n8n fonctionnent nativement.
- **Positive** : Passage de contexte entre nœuds trivial (aucun
  webhook interne, aucun payload à sérialiser).
- **Positive** : Rattachement de V2-ERR simplifié — un seul workflow
  parent à configurer.
- **Positive** : Diagnostic d'erreur facilité — une exécution unique
  visible de bout en bout dans l'onglet Executions de n8n.
- **Négative** : Le workflow deviendra visuellement dense
  (environ 22 nœuds fonctionnels + Sticky Notes). Sera atténué par
  un layout aéré et un code couleur par bloc fonctionnel.
- **Négative** : La testabilité unitaire d'un bloc (ex. V2-IMG seul)
  nécessite l'usage de la fonction `Pin Data` de n8n, plutôt qu'un
  déclenchement direct.
- **Action requise** : Prévoir dans le workflow un layout structuré :
  chaque bloc fonctionnel occupe une bande horizontale, avec Sticky
  Note colorée d'en-tête reprenant l'identifiant du bloc
  (V2-ORCH, V2-SCENE, etc.).

## ADR-V2-03 — Correction C-V2-03 : alignement sur les FK réelles de la V1

**Statut** : ✅ Acté
**Date** : 2026-08-06
**Décideur** : Sterve
**Contexte de la décision** : Audit V2-010 vs réalité Supabase
**Rapport source** : `V2-DEV_Audit_V2-010_vs_Realite_Supabase_2026-08-06.md`

### Problème

L'audit systématique de `05.V2_Implementation_Technique.md` (V2-010)
contre le schéma réel Supabase (via `information_schema`) a révélé
une erreur bloquante sur le nœud **C-V2-03 · Lire Contexte V1** :

- La requête originale référençait `s.campagne_id`, colonne
  **inexistante** dans la table `public.scripts`.
- Elle utilisait `JOIN analyses ON a.contenu_id = s.contenu_id`,
  jointure fragile car `scripts.contenu_id` n'a pas de FK déclarée
  et est typée `bigint` alors que `contenus.id` est en `integer`.
- Le chemin FK réel est :
  `scripts.analyse_id → analyses.id → contenus.id → campagnes.id`
  (trois JOINs nécessaires, pas un).

Sans correction, tout appel du webhook V2 avec un `script_id` valide
aurait échoué avec l'erreur PostgreSQL `42703: column s.campagne_id
does not exist`.

### Décision

La requête C-V2-03 est **corrigée** dans `05.V2_Implementation_Technique.md`
pour utiliser le chemin FK réel :

```sql
FROM public.scripts s
JOIN public.analyses  a    ON a.id    = s.analyse_id
JOIN public.contenus  c    ON c.id    = a.contenu_id
JOIN public.campagnes camp ON camp.id = c.campagne_id
Le SELECT est enrichi de c.campagne_id AS campagne_id, nécessaire
pour l'insertion dans v2_dossiers_production.campagne_id (C-V2-05).

Aucune autre requête de V2-010 n'est impactée. Les 5 clauses
ON CONFLICT et toutes les contraintes UNIQUE ont été vérifiées et
sont conformes. Aucun DDL correctif additionnel n'est requis.

Conséquences
Positive : V2-010 devient 100 % exécutable dans n8n sans
modification supplémentaire. Le bloc V2-ORCH peut être implémenté
dès la prochaine session.
Positive : Formalisation d'une règle de gouvernance :
Aucun nom de table/colonne/FK ne peut être introduit "de mémoire"
dans un document d'implémentation — vérification via
information_schema obligatoire.
Négative : Nécessité de maintenir un historique de version sur
V2-010 (mention "corrigé le 06/08/2026" en en-tête + ADR).
Action requise : Lors de toute future évolution de V2-010,
rejouer l'audit via les 4 requêtes système avant validation.
Document produit dans le cadre du cycle de développement V2.
Toute nouvelle décision d'architecture V2 doit y être consignée avant
implémentation.
