## ADR-V2-01 — Hiérarchie de vérité documentaire

### Contexte
Lors de la conception V2, des divergences ont été identifiées entre :
- le document V2-008 (architecture métier — vocabulaire logique)
- le document V2-010 (implémentation technique — vocabulaire opérationnel)
- la réalité du schéma Supabase

### Décision
La hiérarchie de vérité est établie comme suit, **de la plus forte à la plus faible** :
Supabase (réel) > V2-010 (implémentation) > V2-008 (architecture métier)

text


**Règles dérivées :**
- Le terme `v2_campagnes` est **BANNI** (n'existe pas en base).
- Le terme officiel est `v2_dossiers_production`.
- L'architecture V2 comporte officiellement **7 workflows logiques** :  
  V2-ORCH, V2-SCENE, V2-PLAN, V2-IMG, V2-ANIM, V2-PUB, V2-ERR.
- V2-ORCH comporte 7 nœuds logiques (C-V2-01 à C-V2-05b).

### Conséquences
- Toute contradiction entre docs se résout **en faveur du schéma Supabase**.
- Les documents V2-008 et V2-010 doivent être mis à jour si un écart est détecté.

### Alternatives rejetées
- Rendre V2-008 prioritaire → rejeté : trop conceptuel, s'éloigne de la réalité technique.

## ADR-V2-02 — Pattern d'orchestration n8n

### Contexte
V2-008 décrit 6 workflows métier distincts (ORCH, SCENE, PLAN, IMG, ANIM, PUB).  
Question : faut-il implémenter 6 workflows n8n séparés ou 1 seul workflow monolithique ?

### Décision
**1 seul workflow n8n monolithique**, nommé :
V2 — Créateur de Dossier de Production

text


Il contient tous les nœuds C-V2-01 à C-V2-22, regroupés visuellement par **Sticky Notes colorées** (une par bloc fonctionnel ORCH/SCENE/PLAN/IMG/ANIM/PUB).

**Exception** : V2-ERR reste un workflow séparé, rattaché comme `errorWorkflow`.

### Conséquences
- Debug centralisé (1 seule exécution à suivre).
- Pas de latence inter-workflow (appels HTTP internes évités).
- Structure visuelle claire grâce aux Sticky Notes.

### Alternatives rejetées
- 6 workflows séparés reliés par HTTP → rejeté : complexité + latence + debug fragmenté.
- 6 sous-workflows (`Execute Workflow` node) → rejeté : perte de visibilité en debug.

## ADR-V2-03 — Correction C-V2-03 : alignement sur les FK réelles de la V1

### Contexte
Le document V2-010 (version initiale) proposait pour C-V2-03 la requête :

```sql
SELECT ... FROM scripts s
JOIN campagnes c ON c.id = s.campagne_id;
Problème détecté lors de l'audit du 06/08/2026 : la table scripts n'a pas de FK directe vers campagnes.

Décision
La requête C-V2-03 utilise le chemin FK réel :

SQL

SELECT ... FROM scripts s
JOIN analyses a ON a.id = s.analyse_id
JOIN contenus co ON co.id = a.contenu_id
JOIN campagnes c ON c.id = co.campagne_id;
Chemin FK : scripts.analyse_id → analyses.id → analyses.contenu_id → contenus.id → contenus.campagne_id → campagnes.id

Ajout de c.campagne_id AS campagne_id dans le SELECT.

Conséquences
Le document 05.V2_Implementation_Technique.md (section C-V2-03) mis à jour le 06/08/2026.
Alternatives rejetées
Ajouter une colonne scripts.campagne_id en base → rejeté : dénormalisation inutile, la relation existe déjà via contenus.
🔄 Révision ADR-V2-03 (07/08/2026)
Après vérification empirique des données réelles dans Supabase (19/19 lignes) :

SQL

SELECT COUNT(*) FROM scripts s
JOIN analyses a ON a.id = s.analyse_id
WHERE s.contenu_id = a.contenu_id;
-- Résultat : 19/19 (100% identiques)
Constat : scripts.contenu_id est peuplé à 100% et strictement identique à analyses.contenu_id pour toutes les lignes existantes.

Décision de révision : le chemin FK est simplifié à :

SQL

SELECT ... FROM scripts s
JOIN contenus co ON co.id = s.contenu_id
JOIN campagnes ca ON ca.id = co.campagne_id;
Chemin FK simplifié : scripts.contenu_id → contenus.id → contenus.campagne_id → campagnes.id (2 JOINs au lieu de 3).

Justification
Conformité hiérarchie ADR-V2-01 : Supabase réel > V2-010 → la simplification est autorisée si les données le permettent.
Robustesse : moins de JOINs = moins de points de défaillance.
Performance : requête plus rapide.
Lisibilité : requête plus claire.
Impact documentaire
05.V2_Implementation_Technique.md (section C-V2-03) doit être mis à jour avec la requête simplifiée.
Le workflow n8n V2-ORCH implémente déjà cette version simplifiée (validée en test le 07/08/2026).
ADR-V2-04 — Vérification stricte ID ↔ catégorie pour les outils
Contexte
Lors de la validation fonctionnelle de V2-ORCH (07/08/2026), un bug métier a été identifié dans la version initiale de C-V2-04.

Bug initial : la requête vérifiait uniquement l'existence de 2 outils (1 image + 1 animation) dans le lot, sans contrôler que l'ID reçu dans outil_image_id corresponde effectivement à un outil de catégorie image (et symétriquement pour l'animation).

Cas de bug reproductible :

User envoie outil_image_id=5 (Kling AI = animation en réalité)
User envoie outil_animation_id=1 (Playground AI = image en réalité)
Le total reste : 1 image + 1 animation → passe la vérification
Mais les IDs sont inversés dans le dossier → création silencieuse d'un dossier incohérent
Décision
La requête C-V2-04 utilise désormais des COUNT FILTER explicites qui vérifient le couple (ID, catégorie) :

SQL

SELECT
  COUNT(*) FILTER (
    WHERE id = <outil_image_id>
      AND categorie = 'image'
  ) AS nb_image_valide,
  COUNT(*) FILTER (
    WHERE id = <outil_animation_id>
      AND categorie = 'animation'
  ) AS nb_animation_valide,
  STRING_AGG(nom || ' (' || categorie || ')', ', ') AS outils_trouves
FROM v2_outils
WHERE id IN (<outil_image_id>, <outil_animation_id>)
  AND actif = true;
Un nœud IF · Outils Valides ? est ajouté après C-V2-04 avec 2 conditions strictes :

nb_image_valide == 1
nb_animation_valide == 1
Combinator : AND.

Conséquences
Les IDs inversés (image/animation) sont détectés et rejetés en amont.
Aucun dossier ne peut être créé avec des associations ID ↔ catégorie incohérentes.
Test négatif validé le 07/08/2026 : IDs inversés → False Branch → 0 dossier créé.
Alternatives rejetées
Vérification simple COUNT(*) = 2 → rejeté : n'attrape pas les inversions.
Contrainte CHECK en base sur v2_dossiers_production → rejeté : nécessiterait une jointure runtime coûteuse.
Nœud Aggregate n8n en aval → rejeté : la validation métier doit être explicite en SQL.
ADR-V2-05 — Cardinalité 1-item obligatoire à la sortie de chaque bloc
Contexte
n8n applique par défaut la règle "1 item entrant = 1 exécution du nœud suivant".
Lorsqu'un nœud Postgres retourne N lignes (via SELECT ou INSERT ... RETURNING), les nœuds aval s'exécutent N fois en parallèle.

Bug identifié le 07/08/2026 :

C-V2-04 initial retournait 2 lignes (un outil image + un outil animation).
C-V2-05, C-V2-05b (1/2) et C-V2-05b (2/2) se sont exécutés 2 fois chacun.
Résultat : 2 dossiers créés au lieu d'1, 2 checklists au lieu d'1, 18 étapes au lieu de 9.
Décision
Règle architecturale : chaque bloc du workflow monolithique (ORCH, SCENE, PLAN, IMG, ANIM, PUB) doit garantir en sortie 1 seul item n8n, prêt à être consommé par le bloc suivant.

Méthode privilégiée : agrégation SQL via CTE + SELECT récapitulatif.

Exemple (C-V2-05b (2/2) — Création des 9 étapes de checklist) :

SQL

WITH insertions AS (
  INSERT INTO v2_etapes_checklist (checklist_id, libelle, ordre_affichage, est_realisee)
  VALUES
    (<checklist_id>, 'Scènes générées', 1, false),
    (<checklist_id>, 'Plans découpés', 2, false),
    -- ...
    (<checklist_id>, 'Publication préparée', 9, false)
  RETURNING id, checklist_id
)
SELECT
  <checklist_id> AS checklist_id,
  COUNT(*)::integer AS nb_etapes_creees,
  <dossier_id> AS dossier_id
FROM insertions;
Résultat : 1 seul item avec { checklist_id, nb_etapes_creees, dossier_id }.

Conséquences
Zéro fan-out involontaire entre les blocs.
Chaque bloc peut être testé en isolation avec des sorties prédictibles.
Le passage ORCH → SCENE → PLAN → IMG → ANIM → PUB est déterministe.
Alternatives rejetées
Nœud Aggregate n8n après chaque bloc → rejeté : ajoute un nœud parasite, moins lisible.
Utiliser LIMIT 1 sur les requêtes → rejeté : perte de données, contournement plutôt que solution.
