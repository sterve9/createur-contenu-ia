### DP-V2.1-01 — Vue C minimaliste orientée action

#### Contexte
La Vue "Détail dossier" (C) contenait à l'origine tous les champs techniques du pipeline (`ambiance_visuelle`, `description_visuelle`, `parametres_recommandes`), utilisés uniquement en interne par les LLM.

#### Décision

Les champs pipeline restent conservés en DB mais masqués.

#### Conséquences

### DP-V2.1-02 — Vue F : 3 dropdowns multi-outils

#### Contexte
Lors de la création d'un dossier V2, l'utilisateur doit choisir un script + un outil image + un outil animation. Un même script peut être testé avec plusieurs outils différents.

#### Décision

- Script
- Outil image (lu depuis `v2_outils` filtre `categorie='image' AND actif=true`)
- Outil animation (lu depuis `v2_outils` filtre `categorie='animation' AND actif=true`)

#### Conséquences
- Préserve le cas d'usage "comparer les résultats du même script avec différents outils".

### DP-V2.2-01 — Badges tarifs outils dans dropdown Vue F

#### Contexte
Lors du test end-to-end de la S1 (dossier 8 en V2.1), l'utilisateur découvre en cours de séance qu'il ne sait pas si un outil de génération d'images ou d'animations est **gratuit**, **freemium** ou **payant** avant de le sélectionner. Impact direct sur son budget IA.

La colonne `modele_economique` existait déjà dans `v2_outils` (contrainte CHECK : `'gratuit' | 'freemium' | 'payant'`) mais n'était pas exposée dans l'UI.

#### Décision
Afficher un badge coloré à côté de chaque outil dans les dropdowns image et animation de la Vue F :
- 🟢 **Gratuit**
- 🟡 **Freemium**
- 🔴 **Payant**

Ajouter une légende sous chaque dropdown : `Légende : 🟢 Gratuit · 🟡 Freemium · 🔴 Payant`.

Format label : `Nom outil  —  🟡 Freemium` (séparateur double espace + tiret cadratin pour aération visuelle).

#### Conséquences
- Requête SELECT enrichie avec `modele_economique` (aucun impact perf).
- Fonction utilitaire `construireLabelOutil()` ajoutée côté client.
- Préserve le budget de l'utilisateur et permet un choix éclairé.
- Alignement direct avec le thème V2.2 "utilisabilité au quotidien".

### DP-V2.2-02 — Neutralisation systématique des CTA du créateur source

#### Contexte
Test E2E dossier 10 (S1) — découverte critique : les scripts sources (issus de vidéos YouTube d'autres créateurs) contiennent des CTA spécifiques au créateur original :
- "Rejoins ma communauté Skool"
- "Lien en bio pour le tuto complet"
- "Abonne-toi à ma chaîne Génération IA"
- Noms de programmes, produits, marques personnelles

Ces éléments étaient **recopiés fidèlement** par les LLM :
- Dans la narration voix off (nœud C-V2-06)
- Dans les descriptions plateforme (nœud C-V2-21a)

Résultat : contenu **inutilisable** par l'utilisateur final (risque de mentir à son audience).

**Verbatim user (S1)** :  
> *"L'utilisateur n'a pas la même communauté ni le même lien en bio."*

#### Décision
Ajouter dans les prompts système des nœuds C-V2-06 (Générer Scènes IA) **ET** C-V2-21a (Construire Prompts Publications) une **RÈGLE ABSOLUE — NEUTRALISATION DES ÉLÉMENTS DU CRÉATEUR SOURCE** :

- ❌ **Interdit** : mentions de communautés nommées (Skool, Discord, Patreon, groupes Facebook), "lien en bio" pointant vers un lien spécifique, noms de programme/produit/marque personnelle du créateur source, expressions "ma chaîne", "mon Discord", "mon groupe".
- ✅ **Impose** : CTA génériques réutilisables :
  - "commente si tu veux le tuto"
  - "abonne-toi pour plus de contenu comme ça"
  - "partage si ça t'inspire"
  - "dis-moi en commentaire ce que tu en penses"
  - "sauvegarde cette vidéo pour plus tard"

Objectif : narration et descriptions **100% utilisables sans modification manuelle** par n'importe quel créateur.

#### Conséquences
- Modification de 2 prompts système (C-V2-06 et C-V2-21a).
- Augmentation de `maxTokens` du nœud C-V2-06 (2000 → 3000) pour absorber le prompt rallongé.
- Test E2E dossier 11 validé : plus aucune mention de Skool, Génération IA, lien en bio spécifique.
- Ouvre une nouvelle catégorie de garde-fous "sanitization amont" pour de futurs prompts.

### DP-V2.2-03 — Descriptions plateformes strictement courtes + 5 hashtags max

#### Contexte
Les descriptions générées par le nœud C-V2-21a (V2-PUB) étaient trop longues pour les standards réels 2026 des plateformes cibles, et incluaient trop de hashtags peu ciblés :

| Plateforme | Avant | Cible réelle |
|---|---|---|
| TikTok | max 2200 caractères, 5-10 hashtags | max 300 car, 5 hashtags |
| YouTube Shorts | 200-500 car, 3-5 hashtags | max 150 car, 5 hashtags |
| Instagram Reels | 300-800 car, 8-15 hashtags | max 125 car, 5 hashtags |

Résolution originellement prévue en V2.2-S4, **avancée en V2.2-S1** pour économiser un cycle de pipeline (~4 min de coût IA).

#### Décision
Ajuster le tableau `plateformes` du nœud C-V2-21a avec des contraintes **STRICTES** :

- **TikTok** : titre ≤ 100 car, description ≤ 300 car, exactement 5 hashtags pertinents.
- **YouTube Shorts** : titre ≤ 100 car SEO, description ≤ 150 car, exactement 5 hashtags dont #Shorts obligatoire.
- **Instagram Reels** : caption ≤ 125 car, exactement 5 hashtags pertinents (mix niche + volume).

Ajout d'une phrase finale dans le user_message : *"RESPECTE STRICTEMENT les limites de caractères et le nombre exact de hashtags demandé."*

#### Conséquences
- Résolution de la dette technique DT-V2.1-02.
- Descriptions conformes aux best practices vidéo courtes 2026.
- Meilleure portée organique attendue (hashtags moins dilués).
- Test E2E dossier 11 validé : TikTok ~280 car, YouTube ~145 car, Instagram ~120 car, tous à 5 hashtags exactement.

## ADR-0020 — Gestion robuste du mode "extended thinking" de Claude Sonnet 5

### Contexte
Suite à la mise à jour vers Claude Sonnet 5, le modèle active **automatiquement** un mode "extended thinking" (raisonnement interne étendu) quand le prompt utilisateur devient complexe (règles multiples, contraintes strictes, formats obligatoires). Ce mode se manifeste dans la réponse API par une structure `content[]` contenant plusieurs blocs :

```json
{
  "content": [
    { "type": "thinking", "thinking": "...", "signature": "..." },
    { "type": "text",     "text": "{ ... vrai JSON ... }" }
  ]
}

Deux problèmes observés en V2.2-S1 sur le nœud C-V2-21c (Normaliser Descriptions Publications) :

Consommation invisible de tokens : le bloc thinking consomme des tokens qui ne sont pas visibles dans la sortie, ce qui tronque le bloc text si maxTokens est trop bas. Résultat : JSON coupé au milieu, parsing planté.

Absence défensive du bloc text : le code original faisait content.find(b => b.type === 'text') et plantait avec un message générique en cas d'échec, sans diagnostic.

Décision
Adopter 3 mesures cumulatives de robustesse dans tous les nœuds de normalisation Claude (C-V2-21c en priorité, à étendre à C-V2-07, C-V2-10, C-V2-15c, C-V2-17c si le bug se manifeste ailleurs) :

Concaténer TOUS les blocs text au lieu de prendre le premier :

JavaScript

for (const block of item.json.content) {
  if (block.type === 'text' && block.text) {
    raw += block.text;
  }
}
Extraction robuste du JSON via recherche du premier { et du dernier } :

JavaScript

const firstBrace = raw.indexOf('{');
const lastBrace  = raw.lastIndexOf('}');
if (firstBrace !== -1 && lastBrace !== -1) {
  raw = raw.substring(firstBrace, lastBrace + 1);
}
Diagnostic détaillé en cas d'échec : lister les types de blocs reçus + dump 500 premiers caractères de la structure complète :

JavaScript

throw new Error(
  'Aucun bloc "text" trouvé... Types reçus : [' + contentTypesFound.join(', ') + ']' +
  '. Structure : ' + JSON.stringify(item.json).substring(0, 500)
);
Complément : augmenter maxTokens sur les nœuds Claude concernés (C-V2-21b : 1500 → 2000, C-V2-06 : 2000 → 3000) pour laisser de la marge au raisonnement interne.

Justification
Robustesse aux évolutions modèle : les prochaines versions de Claude peuvent modifier la structure de sortie ; concaténer tous les blocs text est future-proof.
Diagnostic actionnable : en cas de bug futur, les logs indiquent immédiatement si le bloc text est absent ou si le JSON est mal formé.
Récupération élégante du JSON : si un jour Claude ajoute du texte parasite avant/après le JSON ("Voici le JSON demandé : {...}"), le code fonctionne quand même.
Alternatives rejetées
Désactiver le mode thinking via un paramètre : le nœud n8n Anthropic ne l'expose pas actuellement. Solution non testable.
Rollback vers Claude Sonnet 4 : régression de qualité inacceptable sur les autres nœuds.
Retry automatique en cas d'échec parsing : masque le bug sans le résoudre.
Conséquences
Les nœuds Code de normalisation deviennent plus longs (~30 lignes vs ~15) mais plus robustes.
Coût IA légèrement supérieur (tokens du thinking non refacturés séparément, maxTokens augmenté).
Nouveau pattern de code réutilisable à propager sur les autres nœuds Anthropic si besoin.
Documente une surface d'attention pour les futures migrations de modèles LLM.
