## 1. Objectif du document

Ce document décrit précisément chaque composant fonctionnel de la V2.
Pour chaque composant, il spécifie :

- le rôle et la responsabilité ;
- les données en entrée et en sortie ;
- le prompt utilisé (pour les composants IA) ;
- la structure JSON de sortie attendue.

Il constitue la référence directe pour l'implémentation des workflows
V2 dans n8n. Il ne décrit pas la configuration technique des nœuds,
mais le comportement fonctionnel attendu de chaque composant.

Le catalogue des outils image et animation est documenté dans le
document associé `04.1.V2_Catalogue_Outils.md`.

---

## 2. Vue d'ensemble des composants V2

La V2 est composée de six familles de composants :

| Famille | Composants | Workflow |
|---|---|---|
| Orchestration | Réception, Validation, Lecture V1, Initialisation | V2-ORCH |
| Génération Scènes | Générateur Scènes, Normalisateur, Persistance, Redistribution | V2-SCENE |
| Génération Plans | Générateur Plans, Normalisateur, Persistance, Redistribution | V2-PLAN |

| Génération Prompts Animation | Générateur Prompt Animation, Normalisateur, Persistance, Clôture | V2-ANIM |
| Gestion des Erreurs | Capture, Structuration, Journalisation, Isolation | V2-ERR |

## 3. Composants — Workflow V2-ORCH

### 3.1 C-V2-01 · Recevoir Demande V2

**Rôle** : Point d'entrée unique du workflow V2. Reçoit la demande
du créateur via webhook HTTP.

**Entrée** :
POST /lancer-campagne-v2

{
"script_id" : [identifiant entier du script V1 choisi],
"outil_image" : [identifiant texte de l'outil image choisi],
"outil_animation" : [identifiant texte de l'outil animation choisi]
}

text


**Sortie** : Les trois paramètres transmis tels quels au composant
suivant.

**Règle** : Tout appel sans l'un des trois champs est rejeté
sans écriture en base.

---

### 3.2 C-V2-02 · Valider Paramètres V2

**Rôle** : Vérifier que les conditions d'entrée sont réunies avant
tout traitement. C'est le gardien de la frontière V2.

**Contrôles effectués** :

| Contrôle | Condition | Comportement si échec |
|---|---|---|
| Script existant | `script_id` référence une ligne dans `public.scripts` | Rejet — message : "Script introuvable" |
| Campagne V1 terminée | La campagne V1 associée est en statut `TERMINEE` | Rejet — message : "Campagne V1 non terminée" |
| Outil image valide | `outil_image` est présent dans `v2_catalogue_outils` avec `categorie = IMAGE` | Rejet — message : "Outil image non reconnu" |
| Outil animation valide | `outil_animation` est présent dans `v2_catalogue_outils` avec `categorie = ANIMATION` | Rejet — message : "Outil animation non reconnu" |

**Sortie** : Les paramètres validés, enrichis de `campagne_v1_id`
retrouvé depuis `public.scripts`.

---

### 3.3 C-V2-03 · Lire Contexte V1

**Rôle** : Unique point de lecture des données V1. Effectue une
jointure sur trois tables V1 pour constituer le contexte complet
nécessaire à la chaîne V2.

**Lecture effectuée** :
SELECT
s.id AS script_id,
s.script AS script_texte,
a.id AS analyse_id,
a.theme AS theme,
a.mots_cles AS mots_cles,
a.sentiment AS sentiment,
a.score_qualite AS score_qualite,
a.resume AS resume,
c.id AS contenu_id,
c.titre AS titre_contenu,
c.auteur AS auteur_contenu,
c.plateforme AS plateforme_contenu
FROM public.scripts s
JOIN public.analyses a ON a.contenu_id = s.contenu_id
JOIN public.contenus c ON c.id = s.contenu_id
WHERE s.id = [script_id]

text


**Règle** : Ce composant est le seul autorisé à lire dans les
tables V1. Toute évolution de la structure V1 n'impacte
que ce composant.

**Sortie** : Contexte V1 complet transmis à C-V2-04.

---

### 3.4 C-V2-04 · Créer Campagne V2

**Rôle** : Initialiser la campagne V2 en base. Premier écrit
dans les tables V2.

**Écriture** : INSERT dans `v2_campagnes`.

| Champ | Valeur |
|---|---|
| `script_id` | [script_id entrant] |
| `outil_image` | [outil_image entrant] |
| `outil_animation` | [outil_animation entrant] |
| `statut` | `EN_COURS` |
| `execution_id` | [identifiant d'exécution du workflow] |
| `nb_plans_total` | 0 (mis à jour après génération des plans) |
| `nb_plans_traites` | 0 |

**Sortie** : `v2_campagne_id` + contexte V1 complet transmis
au workflow V2-SCENE.

## 4. Composants — Workflow V2-SCENE

### 4.1 C-V2-05 · Générer Scènes IA

**Rôle** : Soumettre le script V1 à l'IA pour le découper
en scènes narratives structurées.

**Modèle utilisé** : Claude Sonnet (cohérent avec V1)

**Prompt système** :
Tu es un expert en narration visuelle et en découpage de scripts
pour vidéos courtes (TikTok, YouTube Shorts, Reels).

On te fournit un script vidéo complet. Ta mission est de le
découper en scènes narratives cohérentes.

Chaque scène doit :

correspondre à une unité narrative distincte ;
avoir une durée estimée réaliste pour une vidéo courte ;
être décrite de façon suffisamment précise pour permettre
un découpage visuel en plans.
Retourne UNIQUEMENT un objet JSON valide, sans texte autour,
respectant exactement cette structure :

{
"scenes": [
{
"numero_ordre": 1,
"titre": "Titre court de la scène",
"description": "Description narrative de la scène",
"ambiance": "Ambiance visuelle dominante (ex: dynamique, posée, dramatique)",
"duree_estimee_secondes": 10
}
]
}

text


**Données injectées dans le prompt** :
- `[SCRIPT]` : texte complet du script V1
- `[THEME]` : thème issu de l'analyse V1
- `[MOTS_CLES]` : mots-clés issus de l'analyse V1

**Sortie brute** : JSON IA à parser par C-V2-06.

---

### 4.2 C-V2-06 · Normaliser Scènes

**Rôle** : Parser la sortie JSON de l'IA, nettoyer les éventuelles
balises markdown, valider la structure.

**Contrôles de validation** :
- Présence du tableau `scenes`
- Présence de `numero_ordre`, `titre`, `description` pour chaque scène
- Valeur numérique de `numero_ordre`

**Comportement en cas d'échec du parsing** : déclenche V2-ERR.

**Sortie** : Tableau de scènes normalisées, prêt à persister.

---

### 4.3 C-V2-07 · Persister Scènes

**Rôle** : Insérer chaque scène dans `v2_scenes`.

**Écriture** : INSERT dans `v2_scenes`.

| Champ | Valeur |
|---|---|
| `v2_campagne_id` | [v2_campagne_id courant] |
| `numero_ordre` | [depuis JSON normalisé] |
| `titre` | [depuis JSON normalisé] |
| `description` | [depuis JSON normalisé] |
| `ambiance` | [depuis JSON normalisé] |
| `duree_estimee_secondes` | [depuis JSON normalisé] |

**Sortie** : `v2_scene_id` pour chaque scène insérée.

---

### 4.4 C-V2-08 · Redistribuer Scènes

**Rôle** : Éclater le tableau de scènes en items individuels.
Chaque item représente une scène à traiter de façon indépendante
par le workflow suivant.

**Sortie par item** :
{
"v2_campagne_id" : [identifiant campagne V2],
"v2_scene_id" : [identifiant scène],
"numero_ordre" : [numéro de la scène],
"description" : [description narrative de la scène],
"ambiance" : [ambiance visuelle],
"theme" : [thème V1],
"mots_cles" : [mots-clés V1],
"outil_image" : [outil image choisi],
"outil_animation" : [outil animation choisi]
}

text

## 5. Composants — Workflow V2-PLAN

### 5.1 C-V2-09 · Générer Plans IA

**Rôle** : Soumettre la description d'une scène à l'IA pour la
découper en plans visuels distincts.

**Modèle utilisé** : Claude Sonnet

**Prompt système** :
Tu es un expert en réalisation vidéo et en découpage technique
de scènes pour vidéos courtes (TikTok, YouTube Shorts, Reels).

On te fournit la description d'une scène. Ta mission est de la
découper en plans visuels distincts et réalistes.

Chaque plan doit :

correspondre à un cadrage ou un angle visuel spécifique ;
avoir une description visuelle précise et actionnable ;
être réalisable avec un outil de génération d'image IA ;
avoir une durée cohérente avec le rythme d'une vidéo courte.
Retourne UNIQUEMENT un objet JSON valide, sans texte autour,
respectant exactement cette structure :

{
"plans": [
{
"numero_ordre": 1,
"description_visuelle": "Description précise de ce qui est visible dans ce plan",
"cadrage": "Type de cadrage (ex: gros plan, plan large, plan américain)",
"ambiance_visuelle": "Ambiance dominante du plan",
"duree_estimee_secondes": 4
}
]
}

text


**Données injectées dans le prompt** :
- `[DESCRIPTION_SCENE]` : description narrative de la scène
- `[AMBIANCE_SCENE]` : ambiance visuelle de la scène
- `[THEME]` : thème V1
- `[MOTS_CLES]` : mots-clés V1

**Sortie brute** : JSON IA à parser par C-V2-10.

### 7.4 C-V2-19 · Incrémenter Plans Traités

**Rôle** : Incrémenter le compteur de plans traités de la campagne
V2 et détecter automatiquement la fin de traitement.

**Écriture** :
UPDATE v2_campagnes
SET
nb_plans_traites = nb_plans_traites + 1,
statut = CASE
WHEN nb_plans_traites + 1 >= nb_plans_total THEN 'TERMINEE'
ELSE statut
END,
date_fin = CASE
WHEN nb_plans_traites + 1 >= nb_plans_total THEN NOW()
ELSE date_fin
END
WHERE id = [v2_campagne_id]

text


**Règle** : Ce composant s'exécute même si le plan courant est
en erreur, afin que la campagne puisse se clôturer correctement
même avec des plans partiellement traités.

## 8. Composants — Workflow V2-ERR

### 8.1 E-V2-01 · Capturer Erreur V2

**Rôle** : Point d'entrée du workflow d'erreur V2. Se déclenche
sur toute erreur survenant dans les workflows V2.

**Données capturées** :
- `execution_id` : identifiant d'exécution n8n
- Nom du nœud en échec
- Message d'erreur brut

---

### 8.2 E-V2-02 · Structurer Erreur V2

**Rôle** : Produire un objet d'erreur structuré et enrichi.

**Structure produite** :
{
"execution_id" : [identifiant d'exécution],
"niveau" : "ERREUR",
"etape" : [nom du nœud en échec],
"message" : [message d'erreur nettoyé],
"v2_plan_id" : [identifiant du plan concerné, si disponible]
}

text


**Règle** : `v2_plan_id` est extrait du contexte si disponible.
Si l'erreur survient avant la création des plans (ex: échec sur
C-V2-05), `v2_plan_id` est null.

---

### 8.3 E-V2-03 · Journaliser Erreur V2

**Rôle** : Insérer l'erreur dans `v2_journal_execution`.

**Écriture** : INSERT dans `v2_journal_execution`.

| Champ | Valeur |
|---|---|
| `v2_campagne_id` | retrouvé via JOIN sur `v2_campagnes.execution_id` |
| `niveau` | `ERREUR` |
| `etape` | [nom du nœud en échec] |
| `message` | [message d'erreur structuré] |

---

### 8.4 E-V2-04 · Marquer Plan En Erreur

**Rôle** : Marquer le plan concerné en erreur dans `v2_plans`.
N'affecte que le plan concerné. La campagne V2 reste en cours.

**Écriture** : UPDATE `v2_plans` SET `statut = ERREUR`
WHERE `id = v2_plan_id`.

**Règle** : Si `v2_plan_id` est null (erreur avant création
des plans), la campagne V2 entière passe en statut `ERREUR`
et `date_fin` est renseignée. C'est le seul cas où une erreur
V2 impacte la campagne entière.

10. Règles transverses
Règle	Description
R-COMP-01	Chaque composant reçoit en entrée uniquement les données dont il a besoin. Aucun composant ne relit la base pour des données déjà transmises par le composant précédent.
R-COMP-02	Tout composant IA retourne un JSON valide. Le composant de normalisation suivant est responsable du parsing et de la validation.
R-COMP-03	Tout échec de parsing ou de validation déclenche V2-ERR.
R-COMP-04	Les conventions d'outil injectées dans les prompts IA proviennent exclusivement du catalogue 04.1.V2_Catalogue_Outils.md.
R-COMP-05	Aucun composant V2 ne modifie les données V1.
R-COMP-06	Le champ notes_createur produit par les générateurs IA est transmis tel quel au dashboard. Il n'est jamais retraité par un autre composant.
Document produit dans le cadre du cycle de conception V2.
Toute modification de ce document doit faire l'objet d'une nouvelle
version avec historisation dans le tracker de projet.
