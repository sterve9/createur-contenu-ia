# 02.3.V2 — Schéma Physique des Données (V2)

## Rôle du document

Ce document décrit la traduction physique du modèle de données V2 en tables PostgreSQL/Supabase.
Il répond aux questions :

- Comment les nouveaux objets V2 sont-ils stockés dans la base ?
- Quelles tables sont ajoutées à l'existant V1 ?
- Quelles sont leurs colonnes, types et contraintes ?
- Quelles relations existent entre les tables V2 ?
- Quelles relations existent entre les tables V2 et les tables V1 ?
- Comment garantir l'intégrité et la cohérence de typage ?

Il sert de référence pour l'implémentation des extensions V2 de la base **PostgreSQL** (schéma `public` de Supabase).

---

## 1. Positionnement par rapport à la V1

Les tables V1 (`campagnes`, `contenus`, `analyses`, `scripts`, `journal_execution`) restent **strictement inchangées**.

La V2 ajoute **9 nouvelles tables**, toutes préfixées par `v2_`, pour :
- éviter toute collision avec les tables V1 ;
- séparer visuellement les périmètres dans Supabase ;
- faciliter les backups sélectifs et l'évolution indépendante.

---

## 2. Conventions techniques V2

Les conventions suivantes s'appliquent à toutes les tables V2 :

- **Préfixe** : toutes les tables sont préfixées par `v2_`.
- **Clés primaires** : `BIGINT GENERATED BY DEFAULT AS IDENTITY` (pas de mismatch de type possible).
- **Timestamps** : `TIMESTAMP WITH TIME ZONE` (timestamptz) systématiquement, avec `DEFAULT NOW()`.
- **Textes** :
  - `TEXT` pour les contenus longs ou variables (prompts, descriptions, textes narratifs, listes de hashtags) ;
  - `VARCHAR(255)` pour les chaînes courtes à sémantique contrainte (noms, catégories, statuts, plateformes).
- **Cascade** : `ON DELETE CASCADE` pour toutes les relations enfant→parent, afin d'assurer un nettoyage propre.
- **Index** : posés systématiquement sur les clés étrangères pour garantir les performances des jointures.
- **CHECK** : posés pour toutes les colonnes à valeurs contraintes (statuts, catégories, modèles économiques).

---

## 3. Anomalies V1 non répliquées en V2

Les anomalies physiques identifiées dans la V1 STABLE sont explicitement **évitées** en V2 :

1. ❌ Pas de mismatch BIGINT/INTEGER entre PK et FK (V2 utilise BIGINT partout).
2. ❌ Pas de `TIMESTAMP WITHOUT TIME ZONE` (V2 utilise systématiquement timestamptz).
3. ❌ Pas d'incohérence VARCHAR/TEXT (règle claire appliquée).

Une seule FK reste en `INTEGER` : `v2_dossiers_production.script_id`, car elle référence `scripts.id` qui est `INTEGER` en V1. Ce choix est **assumé et documenté** pour respecter le typage réel de la V1.

## 5. Table : `v2_dossiers_production`

**Mission** : Enregistrer chaque dossier de production construit à partir d'un script V1.

| Colonne | Type | Contraintes | Description |
|---------|------|-------------|-------------|
| `id` | BIGINT | PRIMARY KEY | Identifiant unique |
| `campagne_id` | BIGINT | NOT NULL, FK → `campagnes.id` ON DELETE CASCADE | Campagne V1 d'origine |
| `script_id` | INTEGER | NOT NULL, FK → `scripts.id` ON DELETE CASCADE | Script V1 utilisé comme base (typage aligné sur la V1) |
| `outil_image_id` | BIGINT | NOT NULL, FK → `v2_outils.id` | Outil choisi pour la génération d'images |
| `outil_animation_id` | BIGINT | NOT NULL, FK → `v2_outils.id` | Outil choisi pour la génération d'animations |
| `statut` | VARCHAR(255) | NOT NULL, DEFAULT 'EN_COURS' | `EN_COURS` ou `TERMINE` |
| `created_at` | TIMESTAMPTZ | NOT NULL, DEFAULT NOW() | Date de création |
| `updated_at` | TIMESTAMPTZ | NOT NULL, DEFAULT NOW() | Date de dernière modification |

**DDL** :
```sql

  id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

  outil_image_id      BIGINT NOT NULL REFERENCES v2_outils(id),
  outil_animation_id  BIGINT NOT NULL REFERENCES v2_outils(id),
  statut              VARCHAR(255) NOT NULL DEFAULT 'EN_COURS',

14. Contraintes d'intégrité (récapitulatif)
14.1 Unicité
v2_outils.nom est UNIQUE (pas de doublon dans le catalogue).
v2_scenes (dossier_id, numero_scene) est UNIQUE.
v2_plans (scene_id, numero_plan) est UNIQUE.
v2_prompts_images.plan_id est UNIQUE (un seul prompt image par plan).
v2_prompts_animations.plan_id est UNIQUE (un seul prompt animation par plan).
v2_descriptions_publication (dossier_id, plateforme_cible) est UNIQUE.
v2_checklists.dossier_id est UNIQUE (une checklist par dossier).
v2_etapes_checklist (checklist_id, ordre_affichage) est UNIQUE.
14.2 Cohérence métier (CHECK)
v2_dossiers_production.statut ∈ {EN_COURS, TERMINE}.
v2_outils.categorie ∈ {image, animation}.
v2_outils.modele_economique ∈ {gratuit, freemium, payant}.
v2_scenes.duree_estimee > 0.
v2_plans.duree_estimee > 0.
14.3 Cascades
Suppression d'une campagne V1 → suppression de tous les dossiers V2 rattachés (et donc de leurs scènes, plans, prompts, descriptions et checklists).
Suppression d'un script V1 → même effet en cascade sur les dossiers rattachés.
Suppression d'un dossier → suppression de tout son arborescence (scènes, plans, prompts, descriptions, checklist).
Suppression d'une scène → suppression de ses plans (et cascade jusqu'aux prompts).
Suppression d'une checklist → suppression de ses étapes.
14.4 Non-cascade (intentionnelle)
Suppression d'un outil (v2_outils) : pas de cascade. Si un outil référencé est supprimé, la suppression échouera tant qu'un dossier ou un prompt l'utilise. Utiliser plutôt le flag actif = FALSE pour désactiver un outil sans casser les références.
14.5 Indexation
Des index sont posés systématiquement sur :

toutes les clés étrangères ;
les colonnes statut, actif fréquemment filtrées ;
les colonnes UNIQUE (implicite via la contrainte).
