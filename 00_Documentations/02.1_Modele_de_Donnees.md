# 02.1 — Modèle de Données

## Rôle du document

Ce document décrit les objets de données qui composent le système ainsi que leurs relations.
Il constitue la représentation **conceptuelle** des informations manipulées par le système, avant toute implémentation technique.

Il répond aux questions suivantes :

- Quelles sont les données principales du système ?
- Quels sont les objets persistants ?
- Quels attributs caractérisent chaque objet ?
- Comment les objets sont-ils liés entre eux ?
- Quelle est la clé d'identification de chaque objet ?
- Quelles informations doivent être conservées dans le temps ?

Ce document ne décrit jamais :
- les tables SQL ;
- les types PostgreSQL ;
- les APIs ;
- les workflows ;
- les scripts.

---

## 1. Objet central

L'objet central du système est :

**Campagne**

Elle représente une demande de veille et de production de contenus, depuis la collecte jusqu'à la génération des scripts finaux.
Tous les autres objets gravitent autour d'elle et lui sont rattachés directement ou indirectement.

---

## 2. Objets de données

### Campagne

**Description**
Représente une opération complète de veille et de production de contenus lancée par un utilisateur pour un sujet, une plateforme et une langue donnés.
Elle porte à la fois les paramètres d'entrée, l'état d'avancement et la finalisation du traitement.

**Attributs principaux**
- `campagne_id`
- `sujet`
- `plateforme`
- `langue`
- `nb_resultats` *(nombre de contenus demandé à la source)*
- `statut` *(EN_COURS, TERMINEE, ERREUR)*
- `nb_contenus_total` *(nombre effectivement collecté)*
- `nb_contenus_traites` *(nombre effectivement analysé et scripté)*
- `date_creation` *(physiquement : `created_at`)*
- `date_fin`
- `execution_id` *(identifiant technique de l'exécution associée)*

---

### Contenu

**Description**
Représente une ressource brute collectée depuis une plateforme tierce (par exemple une vidéo YouTube), rattachée à une campagne.

**Attributs principaux**
- `contenu_id`
- `campagne_id`
- `contenu_source_id` *(identifiant du contenu sur la plateforme d'origine)*
- `titre`
- `auteur`
- `description`
- `date_publication`
- `plateforme`
- `date_collecte` *(physiquement : `created_at`)*

---

### Analyse

**Description**
Représente l'enrichissement sémantique et l'évaluation par l'intelligence artificielle d'un contenu collecté.

**Attributs principaux**
- `analyse_id`
- `contenu_id`
- `resume`
- `theme`
- `sentiment`
- `score_qualite`
- `mots_cles`
- `langue`
- `date_analyse` *(physiquement : `created_at`)*

---

### Script

**Description**
Représente un texte rédigé automatiquement à partir d'une analyse et d'un contenu source, destiné à servir de base à la création d'une vidéo courte (TikTok, Shorts, Reels) ou d'un autre format éditorial.

**Attributs principaux**
- `script_id`
- `analyse_id`
- `contenu_id`
- `script`
- `date_generation` *(physiquement : `created_at`)*

---

### Journal d'exécution

**Description**
Représente la mémoire des événements techniques (principalement les erreurs) survenus pendant le traitement d'une campagne.
Il permet l'audit et le diagnostic sans dépendre du moteur d'orchestration.

**Attributs principaux**
- `journal_id`
- `campagne_id`
- `niveau` *(ex. ERREUR)*
- `etape` *(nom du composant à l'origine de l'événement)*
- `message`
- `date_evenement` *(physiquement : `date`)*

---

## 3. Relations entre les objets

- **Une Campagne** :
  - contient plusieurs contenus ;
  - peut contenir plusieurs entrées de journal d'exécution.

- **Un Contenu** :
  - appartient à une seule campagne ;
  - possède au plus une analyse associée.

- **Une Analyse** :
  - appartient à un seul contenu ;
  - peut produire au plus un script.

- **Un Script** :
  - est rattaché à une seule analyse ;
  - conserve également le lien direct vers son contenu source pour faciliter la traçabilité.

- **Une entrée de Journal d'exécution** :
  - est rattachée à une seule campagne.

---

## 4. Identifiants métier

Chaque objet possède un identifiant unique :

| Objet | Identifiant |
|-------|-------------|
| Campagne | `campagne_id` |
| Contenu | `contenu_id` |
| Analyse | `analyse_id` |
| Script | `script_id` |
| Journal d'exécution | `journal_id` |

La campagne possède également un identifiant technique complémentaire, `execution_id`, qui la relie à l'exécution qui l'a produite. Cet identifiant permet notamment au journal d'exécution de rattacher les incidents à la bonne campagne, sans dépendance à l'état mémoire du moteur d'orchestration.

---

## 5. Cycle de vie d'une campagne

Une campagne peut prendre l'un des trois états métier suivants :

| Statut | Signification |
|--------|---------------|
| `EN_COURS` | La campagne a été créée et son traitement est en cours. |
| `TERMINEE` | Tous les contenus prévus ont été collectés, analysés et scriptés avec succès. |
| `ERREUR` | Un incident a interrompu le traitement ; la campagne est fermée en état d'erreur. |

**Règles** :
- Une campagne débute toujours en `EN_COURS`.
- Elle bascule en `TERMINEE` lorsque le nombre de contenus traités atteint le nombre de contenus total collecté.
- Elle bascule en `ERREUR` si un incident survient pendant le traitement.
- Un statut terminal (`TERMINEE` ou `ERREUR`) n'est jamais réécrit.
- La date de fin est renseignée lors de toute transition vers un statut terminal.

---

## 6. Cycle de conservation

Le système conserve dans le temps :

- les campagnes (paramètres, état d'avancement, dates, statut final) ;
- les contenus bruts collectés ;
- les analyses sémantiques et scores de qualité générés par l'IA ;
- les scripts générés ;
- les événements du journal d'exécution (audit et diagnostic).

Ces informations peuvent être réutilisées pour :
- piloter la stratégie éditoriale ;
- alimenter de nouveaux traitements (ex. régénération de scripts) ;
- analyser les productions passées ;
- diagnostiquer et prévenir les incidents.

---

## 7. Principes de modélisation

Le modèle respecte les principes suivants :

- chaque objet possède une identité propre ;
- chaque information n'est stockée qu'une seule fois ;
- les relations entre objets sont explicites ;
- les objets sont indépendants des technologies utilisées ;
- les objets d'audit (Journal d'exécution) sont distincts des objets métier ;
- le modèle peut évoluer sans remettre en cause les autres objets.

---

## 8. Validation

Le modèle est considéré comme valide lorsque :

- tous les objets métier identifiés dans l'architecture sont représentés ;
- chaque objet possède un identifiant unique ;
- les relations entre objets sont cohérentes ;
- les états possibles d'une campagne sont explicites ;
- les mécanismes d'audit sont représentés ;
- aucune donnée métier importante n'est absente ;
- aucune technologie d'implémentation n'apparaît dans ce document.
