# 02.5.V2 — Contrat des Données (V2)

## Rôle du document

Ce document formalise les **garanties d'échange de données** entre les composants de la V2 et entre la V2 et la V1.
Il définit à un niveau abstrait, indépendant de toute technologie, ce que chaque composant s'engage à fournir et ce qu'il attend en retour.

Il répond aux questions suivantes :

- Quelles données doivent être fournies pour créer une campagne enrichie V2 ?
- Quelles données sont transmises entre les composants V2 ?
- Quelles garanties la V2 attend-elle de la V1 pour fonctionner ?
- Quelles données le Dashboard reçoit-il en retour ?
- Quelles règles de validation s'appliquent à chaque échange ?
- Quels invariants doivent être préservés dans le système ?

Ce document ne décrit jamais :
- les formats techniques (JSON, XML, YAML) ;
- les protocoles (HTTP, WebSocket, RPC) ;
- les workflows n8n ;
- les APIs concrètes ;
- les implémentations techniques.

---

## 1. Positionnement par rapport à la V1

Ce contrat complète celui de la V1 (`02.5_Contrat_des_Donnees.md`) sans le modifier.
Les contrats V1 (webhook de campagne, écriture des scripts, journal d'exécution) restent valides et sont réutilisés tels quels par la V2.

Seuls les **nouveaux contrats introduits par la V2** sont documentés ici, ainsi que le contrat de **lecture des données V1 par la V2**.

---

## 2. Principes généraux des contrats V2

Les contrats V2 respectent les principes suivants :

- **Explicites** : chaque champ échangé possède une signification claire.
- **Complets** : aucun champ obligatoire ne peut être omis.
- **Résilients** : les composants récepteurs doivent gérer proprement les données incomplètes ou invalides.
- **Traçables** : chaque échange est rattachable à une campagne, un dossier ou un composant.
- **Non-régressifs vis-à-vis de la V1** : aucun contrat V1 n'est modifié.

---

## 3. Contrat d'entrée principal : Création d'une campagne enrichie V2

### 3.1 Description
Ce contrat définit les données que le créateur doit fournir pour lancer une nouvelle campagne V2 depuis le Dashboard.

### 3.2 Données attendues

| Champ | Nature | Obligatoire | Description | Règles de validation |
|-------|--------|-------------|-------------|----------------------|
| `sujet` | Texte | Oui | Thème de recherche de la campagne | Non vide, longueur raisonnable |
| `plateforme` | Texte | Oui | Plateforme source de veille (ex. YouTube) | Valeur cohérente avec les plateformes supportées par la V1 |
| `langue` | Texte | Oui | Langue de recherche (ex. fr, en) | Code langue reconnu |
| `nb_resultats` | Entier | Oui | Nombre de contenus à collecter | Entier positif, borne raisonnable (ex. 1 à 20) |
| `outil_image_id` | Référence | Oui | Identifiant de l'outil d'images choisi | Doit exister dans le Catalogue et être `actif = TRUE` avec `categorie = image` |
| `outil_animation_id` | Référence | Oui | Identifiant de l'outil d'animations choisi | Doit exister dans le Catalogue et être `actif = TRUE` avec `categorie = animation` |

### 3.3 Garanties fournies par la V2 en réception
- La campagne est acceptée et enregistrée.
- Les workflows V1 sont déclenchés pour la collecte et l'analyse.
- Un accusé de prise en charge est renvoyé (identifiant de campagne).
- En cas de données invalides, la campagne est refusée avec un motif explicite.

## 4. Contrat V2 ↔ V1 : Garanties attendues des données V1

### 4.1 Description
La V2 s'appuie sur les données produites par la V1 (Campagnes, Contenus, Analyses, Scripts). Elle doit disposer de garanties minimales pour fonctionner.

### 4.2 Garanties attendues de la Campagne V1

| Champ | Garantie |
|-------|----------|
| `campagne_id` | Existe, unique, stable dans le temps |
| `statut` | Prend l'une des valeurs `EN_COURS`, `TERMINEE`, `ERREUR` |
| `nb_contenus_total` | Renseigné après la collecte |
| `nb_contenus_traites` | Reflète le nombre de contenus effectivement scriptés |

**Règle métier** : la V2 ne consulte les scripts d'une campagne **qu'à partir du moment où la campagne est en statut `TERMINEE`**. Une campagne en `EN_COURS` ou `ERREUR` ne doit pas donner lieu à un dossier de production.

### 4.3 Garanties attendues du Script V1

| Champ | Garantie |
|-------|----------|
| `script_id` | Existe, unique, stable dans le temps |
| `script` | Non vide, cohérent narrativement (hook, corps, CTA) |
| Lien avec `analyse_id` | Existe |
| Lien avec `contenu_id` | Existe (pour traçabilité) |

**Règle métier** : la V2 doit pouvoir sélectionner n'importe quel script produit par une campagne V1 terminée.

### 4.4 Ce que la V2 ne modifie jamais
La V2 s'engage à **ne jamais écrire** dans les tables suivantes :
- `campagnes` ;
- `contenus` ;
- `analyses` ;
- `scripts` ;
- `journal_execution`.

Toutes les données V1 sont considérées comme **en lecture seule** pour la V2.

## 5. Contrat entre composants V2 : Découpage → Plans → Prompts

### 5.1 Contrat : Découpage en Scènes → Composant Plans

**Données transmises** :
Pour chaque scène produite par le Découpage, le Composant Plans reçoit :

| Champ | Nature | Obligatoire | Description |
|-------|--------|-------------|-------------|
| `scene_id` | Référence | Oui | Identifiant de la scène nouvellement créée |
| `numero_scene` | Entier | Oui | Ordre dans le script |
| `texte_narratif` | Texte | Oui | Texte à dire |
| `ambiance_visuelle` | Texte | Oui | Ambiance de la scène |
| `duree_estimee` | Entier | Oui | Durée en secondes |

**Règle** : la somme des `duree_estimee` des scènes doit être cohérente avec la longueur du script (ordre de grandeur d'une vidéo courte : 30 à 60 secondes).

### 5.2 Contrat : Composant Plans → Générateurs de Prompts

**Données transmises** :
Pour chaque plan produit, les Générateurs de Prompts reçoivent :

| Champ | Nature | Obligatoire | Description |
|-------|--------|-------------|-------------|
| `plan_id` | Référence | Oui | Identifiant du plan |
| `scene_id` | Référence | Oui | Scène d'appartenance |
| `numero_plan` | Entier | Oui | Ordre dans la scène |
| `description_visuelle` | Texte | Oui | Ce qui est visible dans le plan |
| `duree_estimee` | Entier | Oui | Durée en secondes |
| `ambiance_visuelle_scene` | Texte | Oui | Héritée de la scène pour cohérence |
| `outil_cible` | Référence | Oui | Outil choisi pour la campagne (image ou animation, selon le générateur) |

**Règle** : la somme des `duree_estimee` des plans d'une scène doit être égale à la `duree_estimee` de la scène parente.

### 5.3 Contrat : Générateurs de Prompts → Persistance

**Données transmises** :
Pour chaque prompt généré (image ou animation) :

| Champ | Nature | Obligatoire | Description |
|-------|--------|-------------|-------------|
| `plan_id` | Référence | Oui | Plan associé (un seul prompt image et un seul prompt animation par plan) |
| `outil_id` | Référence | Oui | Outil pour lequel ce prompt a été optimisé |
| `texte_prompt` | Texte | Oui | Instruction complète, prête à copier-coller |
| `parametres_recommandes` | Texte | Non | Paramètres complémentaires |

**Règle** : chaque plan doit à terme posséder exactement un prompt image et exactement un prompt animation.

## 6. Contrat entre composants V2 : Générateur de Descriptions

### 6.1 Description
Le Générateur de Descriptions produit, pour chaque plateforme cible, un ensemble titre + description + hashtags.

### 6.2 Données transmises

| Champ | Nature | Obligatoire | Description |
|-------|--------|-------------|-------------|
| `dossier_id` | Référence | Oui | Dossier de production concerné |
| `plateforme_cible` | Texte | Oui | Nom de la plateforme (TikTok, YouTube Shorts, Instagram Reels, ...) |
| `titre` | Texte | Oui | Titre respectant les contraintes de longueur de la plateforme |
| `texte_description` | Texte | Oui | Description prête à publier |
| `hashtags` | Texte | Oui | Liste de hashtags optimisés pour la plateforme |

**Règles de validation** :
- Le titre doit respecter la longueur maximale autorisée par la plateforme cible.
- La description doit respecter les règles éditoriales de la plateforme.
- Les hashtags doivent être adaptés en nombre et en style à la plateforme.
- Il ne peut y avoir qu'une seule description par (dossier, plateforme).

---

## 7. Contrat entre composants V2 : Création automatique de la Checklist

### 7.1 Description
Lorsqu'un dossier de production est créé, une checklist est automatiquement générée avec un ensemble d'étapes standard.

### 7.2 Structure attendue de la checklist

Une checklist standard V2 contient les étapes types suivantes :

| Ordre | Libellé type |
|-------|--------------|
| 1 | Générer les images (une entrée par plan) |
| 2 | Générer les animations (une entrée par plan) |
| 3 | Assembler les clips dans l'outil de montage |
| 4 | Ajouter les sous-titres |
| 5 | Ajouter les effets et transitions |
| 6 | Valider le rendu final |
| 7 | Publier (une entrée par plateforme cible) |

**Règle** : chaque étape est initialisée avec `est_realisee = faux` et `date_realisation = non renseignée`.
Le libellé de chaque étape peut être personnalisé pour refléter le contenu réel (ex. "Générer image plan 2 - scène 1").

## 8. Contrat V2 ↔ Catalogue d'Outils

### 8.1 Description
Le Catalogue d'Outils est consulté par plusieurs composants V2 (Création de Campagne, Générateurs de Prompts) et doit exposer une structure stable.

### 8.2 Structure exposée par entrée de catalogue

| Champ | Nature | Obligatoire | Description |
|-------|--------|-------------|-------------|
| `outil_id` | Référence | Oui | Identifiant unique |
| `nom` | Texte | Oui | Nom de l'outil |
| `categorie` | Texte | Oui | `image` ou `animation` |
| `modele_economique` | Texte | Oui | `gratuit`, `freemium` ou `payant` |
| `specificite` | Texte | Oui | Point fort principal |
| `description` | Texte | Oui | Présentation courte |
| `actif` | Booléen | Oui | Indique si l'outil est proposé au créateur |

### 8.3 Garanties de contenu

Le catalogue doit toujours proposer, dans chaque catégorie (`image` et `animation`) :
- **au moins un outil `gratuit` actif** ;
- **au moins un outil `freemium` actif** ;
- **au moins un outil `payant` actif** (référence de qualité).

Cette garantie assure l'accessibilité pour le persona ciblé (side-hustler ambitieux) tout en offrant un panel complet.

### 8.4 Règles d'évolution
- Un outil peut être **désactivé** (`actif = FALSE`) mais jamais supprimé s'il est référencé.
- Un outil peut être ajouté à tout moment.
- Les modifications du catalogue n'impactent pas les dossiers de production déjà créés.

## 9. Contrat V2 ↔ Dashboard : Exposition des données

### 9.1 Description
Le Dashboard consomme l'ensemble des données V1 et V2 pour offrir au créateur une vue unifiée de ses campagnes et dossiers de production.

### 9.2 Vue "Liste des Campagnes"

Pour chaque campagne, le Dashboard reçoit :

| Champ | Source | Description |
|-------|--------|-------------|
| `campagne_id` | V1 | Identifiant |
| `sujet` | V1 | Sujet de veille |
| `plateforme` | V1 | Plateforme de veille |
| `statut` | V1 | État de la campagne |
| `nb_contenus_total` | V1 | Nombre de contenus collectés |
| `nb_dossiers_associes` | V2 (agrégation) | Nombre de dossiers créés pour cette campagne |
| `date_creation` | V1 | Date de création |

### 9.3 Vue "Détail d'un Dossier de Production"

Pour un dossier, le Dashboard reçoit :

| Champ | Source | Description |
|-------|--------|-------------|
| `dossier_id` | V2 | Identifiant |
| `campagne_associee` | V1 (via référence) | Résumé de la campagne d'origine |
| `script_utilise` | V1 (via référence) | Contenu complet du script |
| `outil_image` | V2 (via catalogue) | Nom + spécificité de l'outil d'images choisi |
| `outil_animation` | V2 (via catalogue) | Nom + spécificité de l'outil d'animations choisi |
| `statut` | V2 | `EN_COURS` ou `TERMINE` |
| `scenes` | V2 (agrégation) | Liste complète des scènes, avec leurs plans, prompts et durées |
| `descriptions_publication` | V2 (agrégation) | Liste des descriptions par plateforme |
| `checklist` | V2 (agrégation) | Liste des étapes avec leur statut |
| `date_creation` | V2 | Date de création |
| `date_derniere_modification` | V2 | Date de dernière action |

### 9.4 Garanties
- Le Dashboard ne modifie jamais les données V1.
- Le Dashboard peut modifier uniquement : `v2_dossiers_production.statut`, `v2_dossiers_production.updated_at`, `v2_checklists.updated_at`, `v2_etapes_checklist.est_realisee`, `v2_etapes_checklist.date_realisation`.
- Toute autre action de modification déclenche une erreur.

## 10. Invariants du système V2

Les invariants suivants doivent être maintenus à tout moment :

### 10.1 Invariants d'intégrité
- Un dossier de production est toujours rattaché à une campagne V1 existante et à un script V1 existant.
- Un dossier référence toujours deux outils du catalogue existants et actifs (à la création).
- Chaque plan possède exactement un prompt image et un prompt animation.
- Une description existe au plus une fois par (dossier, plateforme).
- Une checklist existe une et une seule fois par dossier.
- Chaque étape de checklist appartient à une seule checklist.

### 10.2 Invariants métier
- La somme des durées des plans d'une scène est égale à la durée de la scène.
- La somme des durées des scènes est cohérente avec la longueur du script.
- Le statut d'un dossier ne peut passer que de `EN_COURS` à `TERMINE` (jamais l'inverse).
- Une étape cochée conserve sa date de réalisation même si elle est décochée puis recochée.

### 10.3 Invariants de séparation V1/V2
- La V2 n'écrit jamais dans une table V1.
- Aucune table V1 ne référence une table V2.
- La suppression d'un objet V1 entraîne la suppression en cascade des objets V2 rattachés.

---

## 11. Règles de validation transversales

Les règles suivantes s'appliquent à tous les échanges V2 :

- Aucun identifiant ne peut être vide ou nul lorsque déclaré obligatoire.
- Aucune référence à un objet inexistant ne peut être acceptée.
- Toute valeur à choix contraint (statut, catégorie, modèle économique) doit appartenir à la liste des valeurs autorisées.
- Les durées doivent être strictement positives.
- Les textes obligatoires ne peuvent pas être vides.
- Les dates de création sont générées par le système, jamais par l'appelant.

---

## 12. Contrat de résilience

En cas de défaillance d'un composant V2, les garanties suivantes s'appliquent :

- Si un générateur de prompt échoue pour un plan, les autres plans ne sont pas impactés.
- Si un générateur de description échoue pour une plateforme, les autres plateformes ne sont pas impactées.
- Une défaillance V2 ne modifie **jamais** les données V1 (elles restent cohérentes).
- Un dossier de production incomplet reste en `EN_COURS` et peut être complété ou repris ultérieurement.
- Le catalogue d'outils doit rester disponible même en cas d'incident, car il conditionne la création de nouvelles campagnes.

---

## 13. Validation

Le contrat des données V2 est considéré comme valide lorsque :

- le contrat d'entrée principal (création de campagne enrichie) est explicite et complet ;
- les contrats entre composants V2 sont formalisés pour chaque étape du flux ;
- les garanties attendues de la V1 sont documentées ;
- le contrat V2 ↔ Dashboard est décrit pour chaque vue exposée ;
- le contrat V2 ↔ Catalogue d'Outils est décrit avec ses règles de contenu ;
- les invariants du système V2 sont explicites ;
- les règles de validation transversales sont documentées ;
- les règles de résilience sont décrites ;
- aucune technologie d'implémentation n'apparaît dans le document.
